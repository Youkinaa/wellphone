# Wellphone 开发问题与决策日志

记录实际遇到的难点、排查过程、方案取舍和验证边界，供后续开发与面试复盘使用。这里解释“为什么这样做”；接口与要求以[主设计](superpowers/specs/2026-09-21-wellphone-design.md)和[运行时契约](superpowers/specs/2026-09-21-agent-runtime-contracts.md)为准，实验版本、原始证据索引和完整数据以[实测报告](validation/2026-09-21-appium-concurrency-probe.md)为准。

## 维护约定

- 发生阻塞、定位根因、修复验证或重要设计变化时更新；同一问题沿用编号，追加日期和新证据，保留之前失败的条件。
- 每条写清现象或约束、证据、根因或未确定项、已尝试与仅比较的方案、决定、状态、验证结果和剩余边界。没有运行过的方案不写成尝试成功。
- 状态区分“已修复并复验”“机制验证通过”“设计已确定、未实现”“已确认缺口、未修复”。通过标准不随结果降低；没有最终解决的问题如实保留。
- 面试表述只压缩已证实的内容，不把设计当实现、合成输入当真人操作、安装成功当业务兼容、局部延迟当端到端性能。
- 只存脱敏结论与证据引用，不复制账号、凭据或原始业务资料。完整版本和统计引用权威报告，避免在多处维护副本。

## 2026-09-21 · J01：单 IME 下如何同时保留主屏输入和副屏中文填写

**状态：机制验证通过；真实 App 与真人拼音输入尚未验收。**

**困难与依据：**目标是在同一个 Android 实例中让用户持续使用主屏，Agent 操作副屏。普通同用户 Android 14 使用单个 IME；`OWN_FOCUS` 不等于禁止副屏抢最高焦点。仅创建副屏，或把 IME policy 改为 `local`，都不能得到两套独立输入法。这是[源码研究确认的平台约束](research/2026-09-21-agent-runtime-and-gui-research.md#23-焦点与中文已有明确系统契约实测范围应收敛)，不是已经发生过“双键盘输入失败”的现场记录。

**比较与实际做法：**分析过副屏软键盘、scrcpy 定向 KeyEvents 和标准控件 `ACTION_SET_TEXT` 的边界。最终给 scrcpy 增加 `STEAL_TOP_FOCUS_DISABLED`，配合 `TRUSTED`、`OWN_FOCUS`；主屏保留 IME，副屏通过 Appium `replaceElementValue` 的 SET_TEXT 路径直接替换 Unicode 文本，再重新定位、读回。没有用全局剪贴板或切换输入法作为运行中的回退路径。

**验证：**在两个不同包的原生 `EditText` 与自制 ProbeIME 上，run-003 的约 60 秒并发中完成 141 轮副屏观察、中文替换、读回和定向点击；主屏 composing、文字、焦点及 IME 会话检查通过。ProbeIME 调用了真实 `InputConnection` 方法，但由脚本点击键盘，不是完整拼音候选词引擎。方法与证据见[实测报告第 2–3 节](validation/2026-09-21-appium-concurrency-probe.md)。

**剩余边界：**真实 App 的 WebView、自绘控件、页面回调和 task 复用可能不满足同样条件。还不能声明三个业务 App 可用、主屏完全不卡，或任意手机均支持；这轮探针没有调用模型/业务 API，也没有使用真实账号。

**面试简述：**“我先把‘两块屏’和‘两套输入法’分开。单 IME 留给用户，副屏用控件语义写中文，再用并发探针验证焦点与输入连接；目前证明的是标准控件机制，真实 App 仍需逐页验收。”

## 2026-09-21 · J02：显示标志已生效，探针却报失败

**状态：探针已修复，并随完整实验复验。**

**现象与证据：**run-001 在检查显示标志时中止，Appium 尚未启动。原断言要求 `DisplayInfo.toString()` 输出包含焦点标志名称；同时 `DisplayDeviceInfo` 已显示相关标志，两个观察结果不一致。

**根因与排查：**核对 Android 14 的 `DisplayInfo.flagsToString()` 后发现，它省略了两项焦点标志。缺少打印名称不能证明运行时 flag 未设置；也不能直接归因于镜像不支持。排查依据见[实测报告第 4 节](validation/2026-09-21-appium-concurrency-probe.md)。

**最终修正：**用[数值读取器](../experiments/display_concurrency/DisplayFlags.java)读取目标 display 的实际 flags，检查必要位 `0x1880` 全部存在，且 PRIVATE 位 `0x4` 未设置；[探针](../experiments/display_concurrency/run_probe.py)仍校验目标显示身份。没有删除必要断言，也没有混用创建时的 VirtualDisplay mask 与最终 Display flags。

**验证与边界：**run-003 读到 `0x1f88`，满足必要位检查，完整实验退出码为 0。flag 正确只是焦点机制成立的前提，不能单独证明所有 App 页面不会跳主屏。

**面试简述：**“一次失败来自观测工具本身：系统打印器漏了字段。我把字符串匹配改成运行时位校验，保留原验收要求，避免把探针误报当平台能力不足。”

## 2026-09-21 · J03：60 秒基线让 Appium 会话提前过期

**状态：实验会话配置已修复并复验；正式 Agent 生命周期管理仍属设计。**

**现象与证据：**run-002 已完成主屏持有 composing 时的副屏写入，以及 60.44 秒主屏基线；进入并发阶段时 Appium session 已失效，并发完成 0 轮。日志明确记录 `New Command Timeout of 60 seconds expired`。

**根因：**基线故意不向副屏发命令，却提前建立了 Appium session；这与默认 60 秒无命令存活期限冲突。它是会话生命周期问题，并非一次中文输入或 HTTP 请求执行超时。

**最终修正：**显式设置 `newCommandTimeout=180`，覆盖本实验的无命令基线。没有增加 HTTP/动作等待，也没有靠失败重试掩盖失效会话。

**验证与边界：**修正后重新执行完整基线与并发阶段，run-003 完成。失败和修正保存在[机器记录的 prior_runs](../experiments/display_concurrency/results/2026-09-21-api34.json)。180 秒适合本探针，不等于正式 Agent 可无限等待用户；等待、关闭、重连、重绑和重新观察的要求见[运行时契约第 5 节](superpowers/specs/2026-09-21-agent-runtime-contracts.md#5-phonesessionobservation-与动作工具)，相关产品实现尚未完成。

**面试简述：**“我先区分会话存活期限和单次动作超时。日志证明 session 在刻意静默的基线里过期，所以调整的是会话配置，并重跑完整实验，而不是笼统把所有超时拉长。”

## 2026-09-21 · J04：副屏读树被主屏活动拖到约 10 秒

**状态：机制探针已采用配置修正，并完成有限对照。**

**现象与证据：**保持主屏持续输入时，把 `waitForIdleTimeout` 恢复为默认 10000，单次副屏 `source` 耗时约 10.1 秒；同一运行中设为 0 的 141 次 `source` 中位数约 121 毫秒。两组样本量不同，完整统计见[实测报告第 3 节](validation/2026-09-21-appium-concurrency-probe.md)。

**根因：**`currentDisplayId` 限定了目标窗口，却没有把 AndroidX 的全局空闲检测改成只看副屏。主屏持续产生无障碍事件，使副屏查询等待全局静默；这不等于用户输入与 Appium 会话互斥。[源码调用链](research/2026-09-21-agent-runtime-and-gui-research.md#74-同时操作会话不互斥但默认等待策略不合适)与实测结果一致。

**最终做法：**探针固定 `waitForIdleTimeout=0` 并回读设置；继续通过 fresh node 和写后读回来确认字段状态。正式运行的副屏前置条件与有界等待要求已写入契约，尚不能把探针当成完整等待器实现。

**验证与边界：**关闭全局 idle 后完成连续并发实验，对照读树也在主屏活动期间执行。默认设置只测了一个样本，因此不能宣称稳定的加速倍数或端到端收益；没有采集主屏帧卡顿数据，也不能据此声称完全无性能干扰。

**面试简述：**“我发现作用域过滤和等待策略是两回事：树只取副屏，空闲等待仍受主屏影响。修正全局 idle 后保留目标状态校验，用局部测量说明收益，不把它包装成整个 Agent 的性能提升。”

## 2026-09-21 · J05：原版 Appium 的正常路径通过，隔离边界仍有缺口

**状态：源码缺口已确认；启动 Toast、特殊文本尾缀、设备端 display/epoch 守卫尚未修复。**

**问题与依据：**[研究第 7 节](research/2026-09-21-agent-runtime-and-gui-research.md#7-复用手机自动化框架与-mcp)发现三处不能从“副屏读写成功”推出的性质：NewSession 会启动全局 Toast 监听，事后关闭仍可能留缓存；文本接口处理字面反斜杠加 `n` 的尾缀时可能触发全局 Enter；元素缓存中的 display ID 不能独自证明刷新后的节点仍属于绑定显示。这些是源码审计发现的缺口，没有把潜在泄露或错路由写成已发生的现场事故。

**已采取的实验措施：**使用原版 Appium server，建立会话后设 `enableNotificationListener=false`，等待原 Toast 缓存过期，再读取合成测试界面；当前探针中文替换成功。关闭监听和等待缓存只能满足这次实验的有限条件，不能证明启动期间未采集主屏内容，也没有覆盖特殊尾缀、旧会话或失效显示的拒绝行为。

**决定与未完成修复：**继续复用 Appium 的树、定位和 SET_TEXT 能力，由有限补丁从启动禁采 Toast 文本、移除隐式 Enter、在设备端校验刷新后的窗口与 session epoch；按键走 scrcpy 定向通道。接口和验收要求归[运行时契约第 5 节](superpowers/specs/2026-09-21-agent-runtime-contracts.md#5-phonesessionobservation-与动作工具)及[验证计划](validation/2026-09-21-feasibility-and-demo.md)。

**验证与关闭条件：**当前只能确认正常路径的合成实验结果。启动期内容隔离、真实换行与字面尾缀、显示失效与旧 epoch 等边界仍需实现并验证；在此之前，G1/G2 不能整体标为通过，也不能把原始 Appium 接口直接开放给 Agent。

**面试简述：**“复用框架不等于继承它的全部默认行为。正常路径通了以后，我继续检查启动、缓存和失败路径，把已验证能力与仍需补齐的隔离边界分别记录。”

## 2026-09-21 · J06：观察优先用树，何时才需要图像

**状态：设计决定，尚未实现观察策略或测量模型收益。**

**设计难点：**标准控件的文本、标识和动作可以从树获得，但行程图片、自绘区域和语义不足的节点需要视觉信息。每步都给模型附截图可能重复传输信息；只依赖树又无法覆盖图片内容。这里记录的是观察方式的取舍，没有把预期成本写成测量结果。

**比较与决定：**采用树优先、按需视觉的观察策略：树足以确认对象和状态时先用树；目标缺失、歧义、图像识别或视觉核验需要时补充副屏截图。区分底层采集/证据留存与本轮模型实际接收的内容，不能将“树优先”理解为禁止取帧。具体观察字段、新鲜度和图像提取约定以[主设计](superpowers/specs/2026-09-21-wellphone-design.md)及[运行时契约](superpowers/specs/2026-09-21-agent-runtime-contracts.md)为准。

**已有依据与剩余边界：**探针证明了指定副屏能够读树与录像，未运行模型选择观察方式的闭环。节点在页面变化后可能失效；树与帧也不是原子快照，不能用旧图坐标继续点击。行程图片用 VLM 直接识别同样只是已选设计，当前没有模型识别正确率、token 成本或真实业务完成率数据。

**面试简述：**“我把可访问性树当默认的语义来源，视觉用来补足树表达不了的内容。同时区分采集、证据保存和模型输入；这个策略已确定，但效果要等模型与真实页面接通后测量。”

## 2026-09-21 · J07：官网 APK 与原 AOSP 模拟器的 ABI 不匹配

**状态：安装阻碍已解决，首次启动与新镜像合成输入机制复验通过；待登录和真实业务验收。**

**最初现象与现场证据：**真实 App 准备阶段，在原 AOSP API 34 AVD 安装官网美团 12.66.202，`adb install` 返回 `INSTALL_FAILED_NO_MATCHING_ABIS`，错误码 `-113`。设备报告 `abilist=x86_64`、`native.bridge=0`；APK 只包含 `arm64-v8a` 原生库。当时状态为“安装受阻，替代镜像验证中”。来源、安装记录与后续状态见[真实 App 准备报告](validation/2026-09-21-real-app-preparation.md)。

**根因与范围：**APK 的原生库架构不在原 AOSP AVD 支持的 ABI 中，且原镜像没有启用原生桥。这一失败发生在安装阶段，尚不能归因于副屏、Appium 或业务页面逻辑，也不能据此断言美团在所有官方模拟器上均不可用。

**2026-09-21 修正与复验：**保留原 AOSP 环境，使用官方 Google APIs API 34 x86_64 r14 镜像新建 `wellphone_api34_apps`。新设备报告 `abilist=x86_64,arm64-v8a`、`native.bridge=libndk_translation.so`；官网下载的美团 12.66.202、腾讯会议 3.46.0.477 均安装返回 `Success`，`am start -W` 均返回 `Status: ok`。截图已确认各自进入隐私/服务协议首次页，证明这两个固定版本在新镜像上能够安装并首次启动。

**验证与剩余边界：**未点击同意协议、未登录、未走业务页面，首次启动不等于真实业务或副屏页面兼容已验收。随后在新镜像独立复跑机制探针：约 60 秒并发中副屏完成 87 轮读写点击，主屏合成输入、焦点和 IME 连续性检查通过，详见[本镜像结果](../experiments/display_concurrency/results/2026-09-21-google-api34.json)。这不是原 AOSP 结果的迁移，也不代表真人拼音、账号登录或真实页面兼容已通过；主屏合成输入吞吐下降仍需后续性能分析。

**面试简述：**“真实 App 预检先遇到了 ABI 门槛：美团官网包只有 ARM64 原生库，原 x86_64 镜像没有原生桥。换用带 ARM64 支持的官方 Google APIs 镜像后，美团与腾讯会议均安装并进入首次协议页；我保留了原失败条件，同时将登录、业务兼容和新镜像并发复验分开验收。”
